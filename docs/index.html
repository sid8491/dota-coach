AI ENGINEERING · CASE STUDY

Real-time game coaching, with an LLM that isn't real-time

Dota 2 streams game state every ~100 ms. A useful LLM tip takes 8–22 s on a local model. Most of this project is the design that makes those two numbers coexist: non-blocking I/O, a stateful event differ, dynamic prompt construction, three-layer output dedup, and post-hoc freshness validation against the latest state.

01 The problem

A pro Dota coach watches your stream and shouts useful things — "TP top now, smoke gank coming", "buy Pike, Lion will hex you". They cost hundreds an hour and you can't have one. Could a local LLM do a smaller version of the same job, live, while you play?

The answer is "yes, but the obvious build doesn't work." You can't just stream game state into an LLM and pipe its replies to your speakers — the latency is wrong by an order of magnitude, the model repeats itself, and half the time its advice is for a fight that's already over. This page walks through the design choices that close that gap.

INPUT

Dota GSI

Game client POSTs JSON every ~100 ms — map, hero, items, abilities, minimap, buildings, events.

SERVER

Flask + thread

Single endpoint POST /gsi/. Returns 200 immediately. LLM call hops to a daemon thread.

BRAIN

Local LLM

Ollama default (qwen3.6:27b / gemma4:e4b); Gemini supported via OpenAI-compat shim.

OUTPUT

Piper voice

Synthesized to a temp WAV, played through winsound — coach in your ear, not on your screen.

Why local? Three reasons. Privacy — game state is detailed and personal. Cost — at one LLM call per 30 s of a 45 min match, cloud bills get real. No network in the hot path — your tip shouldn't depend on residential WiFi during a teamfight.

02 The hard part

CENTRAL TENSION

The LLM is two orders of magnitude slower than the input.

Dota emits a tick every ~100 ms. A 27B local model takes 8–22 seconds to produce one tip. By the time the LLM finishes thinking about "you're at 22% HP", you're either dead or back to full. By the time it answers "3 enemies are missing", they've reappeared. And the model, when asked twice in a row, will happily say the same thing twice.

You cannot make the LLM faster locally. So everything else has to absorb that gap.

The whole system is built around four moves that compensate for a slow brain:

Move 1 · don't queue stale work

Aggressive throttling before the call

An inflight guard + global cooldown + per-trigger cooldown ensure at most one LLM call is ever in progress, no two calls fire within 8 s, and no trigger type repeats within 30 s.

vs. queuing every interesting moment → a 10-tip backlog by minute 5

Move 2 · pack the one call you make

Rich, dynamic prompt construction

One shot is expensive, so each prompt carries phase, lane, K/D/A, ability cooldowns + descriptions, current items, ally/enemy positions, the running enemy lineup, recent events, and the trigger context — pulled from a flat summary dict that's the cross-module contract.

vs. terse prompts that need 3 round-trips to get to a useful answer

Move 3 · re-validate when you hear back

Post-hoc freshness check

The handler always overwrites latest_summary. When the LLM responds 10 s later, we re-check the trigger against current truth: respawned? HP recovered above 60%? enemies back in vision? If yes, drop the tip — better silent than wrong.

vs. trust the LLM's snapshot view → coach yells about a fight that ended 15 s ago

Move 4 · stop the model repeating itself

Two-layer output dedup

Jaccard similarity (≥ 0.65 word overlap) against the last 8 tips drops near-duplicates. A structured pass scans every shipped tip for OpenDota item names and feeds the running "already recommended" set back into the next prompt.

vs. "build Hurricane Pike" three times in a row

04 End-to-end flow (per tick) main.py →

One-way per request. The Flask handler returns 200 immediately; the LLM call hops to a daemon thread so a slow model never backs up GSI's POST loop. The live ticker below is a fake stream of what the console actually prints during a match.

STAGE 01🎮

GSI POST

Dota client POSTs JSON ~10×/sec to http://127.0.0.1:8000/gsi/ with auth token.

STAGE 02🧹

Summarize

filter_minimap drops ward/creep/rune icons. summarize() flattens to a contract dict.

STAGE 03📊

Diff & emit events

EventDiffer.process compares prev↔curr, emits typed events (death, low_hp, …).

STAGE 04🧠

Gate + LLM

Coach.maybe_advise applies cooldowns + inflight guard, picks one trigger, calls LLM on a thread.

STAGE 05🔊

Filter + speak

Drop OK, stale, or duplicate tips. Survivors → log + Piper TTS.

main.gsi() in code form

data    = request.get_json(...)            # raw GSI tick
auth    = data["auth"]["token"]            # 401 on mismatch
data["minimap"] = filter_minimap(...)      # drop wards/runes/creeps
curr    = summarize(data)                  # → flat dict contract
matchid = curr["matchid"]                  # → rotate log if new match
events  = differ.process(curr)             # stateful diff
coach.maybe_advise(curr, events)           # → daemon thread for LLM
print_snapshot(curr)  # every 30s in ACTIVE_GAME_STATES
return ("ok", 200)                         # never block on LLM

05 What wakes the LLM events.py →

  
You can't run the LLM every tick — it costs 8–22 s and you'd queue a 50-deep backlog inside a minute. Instead, a stateful EventDiffer compares each tick to the previous one and emits typed events. A subset (17 types) wakes the model; the rest are logged for reference.


  
Three sources of events

  

    
Diff-derived
Compare prev↔curr summary: KDA changes, level-ups, HP/MP crossing thresholds, ult coming off cooldown, item gained/lost, building lost, status flag flip.

    
Server-event derived
From GSI's events array: Roshan killed, Aegis picked up, hero kills, tower/rax kills, ward kills, courier events — each dedup'd by sorted-KV tuple.

    
Derived & periodic
enemies_missing fires after ≥ 2 enemies are off-map for ≥ 5 s. periodic_check fires every 120 game-seconds — guarantees a strategic check-in in quiet stretches.

  


  
Triggers that wake the LLM

  

    deathlow_hplow_mp
    ult_readyaghsshard
    level_up*talent
    roshan_killedaegis_picked_up
    our_building_fellfirst_blood
    smokedenemies_missing
    periodic_checkkill
    team_kill
  

  
* level_up only fires at milestone levels {2, 6, 10, 12, 15, 18, 20, 25} — the levels that actually unlock something.


  
Why debounce vision and status?

  
GSI's minimap and status flags flicker. A hero on the edge of vision blinks on and off every other tick; a Razor static link debuffs you for half a second and the model would be told "you're disarmed" five times in a row. Both go through a debounce: the change must persist for 2 s (status) or 3 s (vision) before an event is emitted. Server events get a different dedup — keyed by their sorted KV tuple, capped at 500 entries.







  
06 Prompt construction coach.py · SYSTEM_PROMPT →

  
One LLM call is expensive, so we pack each one. The system prompt is fixed; the user message is assembled per-call from the current summary, recent events, recent tips, the running enemy lineup, and the trigger that woke it.


  
System prompt — what doesn't change

  
    
    
  • Output contract: one tip, one or two short sentences. No greeting, no padding. Reply just OK if there's nothing useful to add — gives the model an explicit "decline" path so it doesn't fill silence with fluff.
    • 
    
  • Visibility rules: own hero fully known; enemy HP/items/mana never visible to GSI; ally items/HP not visible. Stops the model from making up information it can't have seen.
    • 
    
  • Hallucination clamp: "only suggest abilities/items that appear in the user message." The user message lists the full ability + item set, so this constrains the model to the actually-castable kit.
    • 
    
  • Per-trigger focus block: per-type instructions — death → respawn decision; low_hp → immediate escape; ult_ready → where/whom; periodic_check → next item OR strategic call.
    • 
    
  • Few-shot pairs: good/bad examples that punish empty advice ("save it for the right moment") and reward specifics ("Snipe from fog with Assassinate — they're alone, you have 1700 range").
    • 
  


  
User message — what changes every call

  
The blocks below land in _build_prompt()'s output, in this order. The three marked ★ are the interesting ones — they're the channels we use to teach the model from its own past output.

  

    
Game contextphase (PRE/EARLY/MID/MID-LATE/LATE), hero + roles + attribute, lane bucket, facet, clock, score, day/night, level, HP%/MP%, status flags, K/D/A, CS, gold, GPM

    
Your abilitiesname + dname, level, ult/passive flag, cooldown ("off cd" or "ON CD Xs"), first-sentence description from OpenDota

    
Your itemsdisplay names of equipped items (no empty slots)

    
Allies in visionhero short name + lane bucket — only those visible on the minimap

    
Enemy lineupunion of every enemy hero ever seen this match — so the model knows the full opposing 5 even if only 2 are visible right now

    
Visible enemiesN/5 currently visible + N missing + per-hero lane bucket

    
Recent eventslast 8 typed events (e.g. level_up: Leveled to 6)

    
Recent tips ★last 8 tips already given this match — "DO NOT repeat or rephrase, give a DIFFERENT angle"

    
Already-recommended items ★every item dname this match's prior tips named — model must pick something else

    
Trigger"type: msg" e.g. periodic_check: periodic check-in

    
Trigger tail ★periodic_check gets an extra "(a) build [item] next or (b) push/smoke/defend [lane]" framing tail — forces structured choice instead of vague strategy talk

  


  
★ The three feedback channels worth talking about

  
Recent tips closes the loop on self-repetition. The model can't see its own outbox; we forward it.

  
Already-recommended items is the structured layer of dedup. After every shipped tip, we scan the text against OpenDota's full item-dname set (lowercase, word-boundary'd) and stash the hits — then surface them on the next call so the model picks something else.

  
Trigger tail is per-type prompt engineering. For periodic_check, "give one of (a) build [item] next or (b) push/smoke/defend [lane]" turned vague strategy talk into concrete asks. Worth adding for other trigger types as patterns emerge.







  
07 Output quality control coach.py · _stale_reason →

  
The model's response goes through three independent filters before anything is spoken aloud. Each catches a different failure mode. Tips lost here are logged with the reason, so you can see exactly why the coach went quiet.


  

    

      
Filter 1 · model declined

      
Empty content / "OK"

      
If the model returns empty content, we log thinking and done_reason so silent drops are visible (thinking models put their output in the wrong field if think:false is ignored). If it returns the literal "OK", we honor the decline.

    

    

      
Filter 2 · state already changed

      
Post-hoc freshness check

      
The handler always overwrites latest_summary on every tick. When the LLM responds, _stale_reason() re-checks the trigger against current truth — not against the summary the prompt was built with. If the player respawned, HP ≥ 60%, MP ≥ 50%, or fewer than 2 enemies are still missing, the tip is dropped.

    

    

      
Filter 3 · model is repeating itself

      
Jaccard + structured dedup

      
Jaccard similarity over word sets, threshold 0.65, against the last 8 tips. Survivors are scanned for OpenDota item names; matches go into recommended_items and reappear in the next prompt as the "don't suggest these again" list.

    

  


  
Why three filters?

  
Because each catches something the others miss.

  
    
    
  • "OK" filter catches the model deciding nothing useful applies — without an explicit decline path, the model fills silence with empty advice.
    • 
    
  • Freshness filter catches the latency gap. The model can't know that 12 s have passed since the prompt was built. If you trust the model's word, the coach yells about fights that ended 15 s ago.
    • 
    
  • Similarity + structured dedup catches the model's preference for safe, repeated phrasing. Jaccard catches near-rephrases; the item-name pass catches "build Pike" → "go for Hurricane Pike" → "Pike is the next item" all as the same recommendation.
    • 
  


  
The filter funnel in code form

08 Concurrency & backpressure coach.py · maybe_advise →

  
GSI POSTs every ~100 ms. The LLM takes 8–22 s. Without backpressure you'd accumulate a 50-call queue inside a minute. Five mechanisms prevent that.


  

    
🔒Inflight guardAt most one LLM call ever in progress (self._inflight + threading.Lock)

    
⏱️Global cooldownMIN_INTERVAL_SEC = 8 game-seconds between any two calls

    
🎯Per-trigger cooldownPER_TRIGGER_COOLDOWN_SEC = 30 — death tips don't fire 4× during one respawn window

    
⚡200 immediatelyFlask handler returns before LLM call starts — GSI's POST loop never blocks

    
🧵Daemon threadSimple. No event loop, no asyncio. Lifecycle tied to the process — no zombie threads on shutdown.

  


  
Why threads over asyncio?

  
The hot path is I/O-bound on exactly one slow operation (the LLM HTTP call) at a time. There's no fan-out, no concurrency between calls, no upstream that benefits from cooperative scheduling. Threads keep the rest of the code synchronous and avoid coloring every consumer with async. The TTS path uses the same pattern — one daemon thread per speak(), serialized internally by a single _lock so tips don't talk over each other.







  
09 Provider routing coach.py · _call_llm →

  
Default is Ollama (local). Switching to Gemini — or any OpenAI-compatible endpoint (OpenRouter, OpenAI) — is a one-line env var change because dispatch is keyed on the model name.



def _is_gemini_model(model):
    return model.startswith("gemini-") or model.startswith("models/gemini-")

def _call_llm(model, user_msg, timeout=120):
    if _is_gemini_model(model):
        return _call_openai_compatible(GEMINI_URL,
            {"Authorization": f"Bearer {GEMINI_API_KEY}"}, model, user_msg, timeout)
    return _call_ollama(model, user_msg, timeout)

10 Observability

  
Every drop is logged with a reason. That's deliberate — silence in a coaching tool is ambiguous (was nothing happening? did the model crash? is it just throttled?). Each filter prints its own diagnostic, and per-match logs make post-game review tractable.


  

    
Per-match log rotation
Boots into logs/session_<ts>.log. On the first GSI tick with a matchid, switch_to_match() renames it to <matchid>.log, carrying pre-game content forward only from a session_* file. Match-to-match transitions get a clean cut.

    
Raw GSI capture
Opt-in via RAW_GSI_ENABLED=1. Writes every POST body as one JSON line to logs/<matchid>_raw_gsi.jsonl — useful for replay, prompt-engineering iteration, and building eval sets.

  


  
Diagnostic messages worth knowing

  

    
Log lineWhat it tells you

    
[COACH][model] tip…A tip survived all filters and is being spoken.

    
[coach] {model} declined (OK)Model explicitly returned "OK" — not a bug.

    
[coach] empty content from {model} (done_reason=…, thinking_excerpt=…)Model returned nothing. thinking_excerpt shows what it was thinking about — useful for tuning num_predict or switching off thinking models.

    
[coach] dropped stale {type} tip ({reason})Freshness filter killed it. Reason explains which condition: respawned, HP recovered to X%, etc.

    
[coach] dropped duplicate tip: …Jaccard similarity ≥ 0.65 against a recent tip.

    
[coach] ollama unreachable at {url}Ollama daemon is down. Coach silently keeps trying.

  


  
Werkzeug's per-request 200-OK access logger is silenced (set to WARNING) in logger.setup_logging() — otherwise the log would be 99% access spam.







  
11 What's next

  
Honest gaps. None of these are blocking; each is a real next step.


  

    
EVAL
Tip-quality eval harness
Replay captured {matchid}_raw_gsi.jsonl files against a held-out set; score tips by rubric (specific? actionable? hallucinated abilities/items? freshness?). Today quality is judged by ear, which doesn't scale.

    
A/B
Prompt & model A/B
Run two configurations side-by-side against the same replay, diff the tip streams. Today the only way to compare is to play two matches.

    
LATENCY
Streaming + mid-flight cancel
Stream tokens; cancel the call when _stale_reason() becomes true mid-generation. Currently a slow tip burns the full latency budget even when it'll be dropped on arrival.

    
DEDUP
Embedding-based similarity
Jaccard catches near-duplicates but misses paraphrases ("escape to base" vs "TP home"). A small embedding model + cosine threshold would catch both.

    
RAG
Hero / matchup knowledge
Retrieve hero-specific guides + matchup priorities into the prompt. Today the model relies on parametric knowledge — small models guess Earth Spirit's Magnetize from the name.

    
FEEDBACK
In-game tip rating
A hotkey to thumbs-up / thumbs-down the last tip; collect those into a preference dataset for fine-tuning or DPO down the line.

    Events & slot-inference — full reference
    
EventDiffer is stateful — it holds prev, debouncing buffers, an emitted-server-event dedup set capped at 500, and a slot_to_hero map it builds up over the match. It only diffs when both ticks are in ACTIVE_GAME_STATES (pre-game and post-game are intentionally inert). A change in matchid triggers _reset().

Slot → hero inference

    
GSI exposes player slots (0–9) but not always the hero behind them. The differ builds slot_to_hero by (a) the player's own hero, (b) observing victim/killer slots on CHAT_MESSAGE_HERO_KILL when exactly one hero of that side just vanished from the minimap, and (c) elimination once 5 enemy heroes have been seen.

  


  
Modules


  

    TTS pipeline
    
Piper synthesizes to a temp WAV, winsound.PlaySound plays it, then the WAV is deleted. A single _lock serializes playback so tips don't talk over each other. Each speak() call spawns its own daemon thread, so the coach pipeline is never blocked by audio.

    

      
DEFAULT
en_US-amy-medium
ONNX + JSON sidecar under models/. Override with $env:PIPER_MODEL.

      
FALLBACK
Missing voice
No exception — prints [tts] model not found and silently disables speech. Tips still log.

      
KILL SWITCH
TTS_DISABLED=1
Set the env var to mute the run entirely. Useful for development.

    

  


  

    Logging behavior
    
setup_logging() must run before importing coach — otherwise coach's module-level prints don't get captured. main.py respects that import order.

    
    
      
  • Logs go under logs/ (auto-created).
    • 
      
  • Pre-match output writes to logs/session_<timestamp>.log.
    • 
      
  • On the first tick that exposes a matchid, switch_to_match() renames the session log to <matchid>.log — carrying pre-game content forward only from a session_* log, never from a previous match's log.
    • 
      
  • Both stdout and stderr are tee'd via the _Tee class → console + file.
    • 
      
  • Werkzeug's per-request access logger is set to WARNING in the same function, to silence the 200 - spam.
    •

    Configuration — env vars and tunable thresholds
    
PowerShell only. set VAR=... is cmd.exe syntax and silently no-ops here. Always use $env:VAR = "...". main.py loads .env with override=True before importing coach — so .env wins over pre-existing shell vars.

    

      
DOTA_COACH_MODEL
Default: qwen3.6:27b
Ollama tag, or a gemini-* model name to switch providers.

      
OLLAMA_URL
Default: http://localhost:11434/api/chat
Override only if Ollama is on a non-default host/port.

      
GEMINI_URL
Default: Google's OpenAI-compatible endpoint
Any OpenAI-compatible chat-completions URL works (OpenRouter, OpenAI, …).

      
GEMINI_API_KEY
Required when using a gemini-* model
Sent as Authorization: Bearer ....

      
DOTA2_GSI_TOKEN
Default: a placeholder shared with the cfg
Must match auth.token in the GSI cfg file.

      
PIPER_MODEL
Default: models/en_US-amy-medium.onnx
Absolute or relative path to any Piper ONNX voice.

      
TTS_DISABLED
Default: unset
Set to 1/true/yes to mute audio entirely.

      
RAW_GSI_ENABLED
Default: unset
Set to 1/true/yes to dump every raw GSI POST to logs/<matchid>_raw_gsi.jsonl.

    Extending the coach (add a trigger, add a field, …)
    
Add a new trigger type:

    
    
      
  1. Decide where to detect it. Diff-based? Add to a _diff_* method on EventDiffer. Server-event? Add a branch in _parse_server_event. Derived? Extend _derived_triggers.
    2. 
      
  2. Emit it with self._ev(clk, "your_type", "human-readable msg", ...extra).
    3. 
      
  3. Add "your_type" to coach.TRIGGER_TYPES so the gate considers it.
    4. 
      
  4. Add a one-line bullet to SYSTEM_PROMPT's "Trigger-type focus" section telling the model what to do for it.
    5. 
      
  5. If it can be "stale" by the time the LLM responds, extend _stale_reason().
    6. 
    


    
Add a new field to the summary contract:

    
    
      
  1. Populate it in extract_info.summarize().
    2. 
      
  2. Make every consumer tolerate it being missing (older captured logs may not have it).
    3. 
      
  3. Read it in EventDiffer if it produces events.
    4. 
      
  4. Surface it in coach._build_prompt if the model should know about it.
    5. 
      
  5. Optionally print it in extract_info.print_snapshot for the 30-second console summary.
    6.
